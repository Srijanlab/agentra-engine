- Deterministic control flow in plain Python for anything that must not silently fail or drift (circuit breakers, cost caps, prod-promotion gating, retry-on-contradictory-CLI-result logic) — prose/system-prompt instructions are explicitly distrusted for safety-critical invariants ('never deploy before local tests pass' is a real boolean check, not a prompt rule). - Safety is layered: Docker container isolation is primary; a regex-based PreToolUse hook (not the SDK's can_use_tool, which is silently bypassed under bypassPermissions mode) is defense-in-depth secondary. - Persistent state is deliberately split by ownership: agentra's own cross-app bookkeeping goes to Firestore/local-JSON (AGENTRA_HOME), while a target repo's product knowledge (bugs, features, shipped work) lives entirely in that repo's own GitHub Issues/Variables with no local mirror — 'project knowledge belongs with the project.' - Only 4/5 originally-planned local memory categories (architecture/decisions/features/metrics/failures) survived after auditing which ones actually had readers; unused write-only ledgers were deleted rather than kept 'just in case.' - Two parallel orchestration strategies coexist on purpose: a fixed hardcoded pipeline and an LLM-driven dynamic planner, so there's always a deterministic fallback path. - Testing agent runs in two independent passes (local test suite, then live pre-prod verification) rather than one, treating 'code passes tests' and 'the actual deployed thing works' as genuinely different claims. - Production is reachable from exactly one code path (auto-remediate hotfix promotion) and is structurally excluded from the LLM brain's own tool menu, not just discouraged by instruction. - Human-in-the-loop escalation (GitHub issue #34) deliberately has no inbound Slack Events API receiver and no new public webhook in this pass: connectors/slack.py is outbound-only (best-effort chat.postMessage, silently skipped if unconfigured, never raised as a run failure), and the two answer channels that resume a waiting_for_human run are the dashboard's 'Needs your input' panel (POST /apps/{app}/human-input) and a plain GitHub issue comment polled by the existing /trigger/scheduled tick (server/routes/triggers.py's _reconcile_human_input_for_app, ~every 15 minutes via compute.tf's agentra-trigger-loop, no new infra). Resume-correlation state (app id, run_id, branch, session_id, the original tracking issue, the question) is stamped onto the needs_human GitHub issue itself as a structured comment (memory/issues.py + connectors/github_issue_lifecycle.py), not a new database collection, so it stays the single source of truth. FOLLOW-UP (not built): true Slack-thread-reply-driven resume (a human replying in the Slack thread itself, instead of the dashboard or a GitHub comment) would require a new inbound Slack Events API endpoint, which needs its own security review before it's added -- Slack request signature verification (X-Slack-Signature/X-Slack-Request-Timestamp per Slack's signing-secret scheme), replay-attack protection (timestamp window + nonce/dedup, since a valid signed request can otherwise be re-sent), and routing a bare thread-reply payload back to the correct waiting run/session unambiguously. Do not add a `/slack/events`-style route without that review. - Claude Code CLI auth/login failures (GitHub issue #42, e.g. "Not logged in · Please run /login") are detected as a distinct class everywhere an agent subprocess can be invoked, not just at the top-level autonomous-cycle call: agents/base.py's run_agent sets AgentResult.auth_failure=True and returns immediately with zero retries (a fresh subprocess would hit the exact same missing credentials), and agents/brain/tools.py's _check_auth_failure (called right after every one of the nine tool-wrapped agents' calls) plus run_autonomous_cycle's own top-level query() handler both route it through Memory.record_failure instead of the ordinary per-tool failure path, ending that cycle immediately (bypassing MAX_CONSECUTIVE_TOOL_FAILURES entirely -- waiting for a second failure would only burn more cost for no benefit). Memory.record_failure itself reuses GitHub issue #34's Slack human-in-the-loop channel for this specific failure class: an auth failure always gets filed as a needs_human + blocking_agentra bug (which makes the *next* cycle's blocking_bugs() pre-flight check refuse to start at all until a human runs `claude /login` and clears it) and, only for a genuinely new occurrence (guarded by the same difflib-based _find_similar_open_bug dedup record_known_bug already uses), an outbound Slack message with the literal actionable text "Claude Code session is not authenticated on this runner -- run /login and re-trigger." This intentionally does not attempt to fix credential provisioning itself -- that's an infra/human decision, not something agentra should silently work around.
