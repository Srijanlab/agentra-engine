This IS agentra's own source code -- the system managing this repo is the same system running in it (self-hosted/dogfooding).

Deployment: Compute Engine VM (agentra-orchestrator, us-east1-b), not Cloud Run -- migrated off Cloud Run to allow subscription-based `claude login` auth instead of API-key billing (Cloud Run has no interactive exec). Pipeline: Dockerfile (multi-stage: builds agentra/web/ React app via Node, then the Python package, then installs Playwright/Chromium for the Testing Agent's pre-prod screenshots) -> Cloud Build (deploy/gcp/cloudbuild.yaml) -> Artifact Registry -> SSH into the VM (`gcloud compute ssh agentra-orchestrator --zone=us-east1-b --tunnel-through-iap`) -> pull the new image and recreate containers.

Four containers run together on that VM, and a redeploy MUST recreate all four, not just the app: `agentra` (the server itself), `cloudflared` (public ingress tunnel), `agentra-trigger-loop` (a local cron substitute -- posts to /trigger/scheduled every 15 min, fanning out to every registered app), and `agentra-pubsub-pull` (pulls the work-queue subscription). The last three join `agentra`'s network namespace via `--network container:agentra`, which pins to that specific container's ID at creation time -- recreating only `agentra` without also recreating the other three leaves them silently attached to a dead namespace (every request fails closed, no error surfaced). This actually happened once and broke the scheduler for an unknown period before being diagnosed.

The existing deploy_pre_prod/promote_prod tools only know Vercel/Firebase CLIs, so they correctly report "skipped" for this repo -- deploying a real change to agentra itself is not yet autonomous; it requires a human running the steps above.
