- Dual-path storage: nearly every registry/memory write function branches `core._ddb is not None` (DynamoDB) vs. local JSON — same function signature either way, so callers never know which backend is live.
- Auth is layered as a middleware chain, evaluated in order: `check_verify_token` (scoped read-only pre-prod bypass) -> public-path allowlist -> Firebase ID-token verification -> per-route bearer gates (`/internal/*`, `/trigger/queue`, `/trigger/cron`, `/trigger/alarm`) that live outside the Firebase gate entirely, each with its own tiny module rather than one central switch.
- The engine/loop boundary is enforced structurally, not just by convention: `registry.enqueue_job` + a whitelisted `/internal/rpc` method-name set (`_REGISTRY_METHODS`/`_MEMORY_METHODS`) is the only channel the loop has into engine state; no shared DB credentials or GitHub App key ever leave the engine process.
- Job leasing uses a CAS-based claim (`pending -> claimed`) plus a per-app (not per-job) heartbeat ceiling and bounded attempt count, so a stuck job self-heals into either a retry or a terminal human-escalated failure rather than hanging forever.
- Per-app LLM backend selection is modeled as a map keyed by SDLC agent id with graceful migration from a legacy flat field, letting different pipeline stages (implementation vs. testing vs. discovery) run on different model backends without a schema break.
- Scheduling is unified behind one pure function (`compute_schedule_status`) consumed by both the cron enqueue path and the read-only dashboard endpoint, with continuous-mode (`schedule_continuous`) handled as an alternate due-time formula inside the same function rather than a parallel code path.
- Request payload models are split into a dedicated `_payloads.py` module per route file to keep files under the repo's 500-line/SRP limit (per `CLAUDE.md`), rather than inlining Pydantic models in the route handlers.
